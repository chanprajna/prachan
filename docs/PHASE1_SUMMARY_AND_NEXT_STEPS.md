> **建立日期**: 2026-04-05
> **專案狀態**: ✅ 第一階段（前端 UI 與 UAT 測試版）已全數開發完成。
> **目的**: 紀錄目前為止的所有開發歷程與設計決策，並做為未來（可能是一個月後）重啟開發「階段二：後端與資料庫串接」時的重要指引。

## 壹、目前開發成果總結 (Phase 1 Achievements)

我們採用了「前端 UI Mock 先行」的策略，已經完成了所有核心頁面的骨架與互動流程。所有資料目前皆以假資料（儲存於 `lib/mock/data.ts`）呈現，主要目的是提供給終端使用者（悅眾、專職、義工）進行操作體驗確認。

### 1. 核心設計規範落實
*   **現代禪風 (Modern Zen)**：以深綠色 (`#2D5A5A`)、大地茶色 (`#5E5345`) 與石灰白為主色調，圓角設定為 `2xl`，強調乾淨與留白。
*   **深色模式 (Dark Mode)**：已透過 `next-themes` 全域導入，針對所有元件進行暗黑模式下的顏色自動反轉。右上角帶有太陽/月亮切換鈕。
*   **以菩薩為中心設計**：為適應 40-70 歲的主力受眾，全站採用 `text-lg` 以上之字體、`h-14` 以上之按鈕。且所有重要操作（如建立、停用、提交意願）均綁定原生的**中文防呆確認提示框**。

### 2. 已完成的功能畫面

| :--- | :--- | :--- |

### 3. 特別開發的 UAT 輔助工具
為了方便展示給使用者看，系統右下角已實作 **「Mock 角色切換器 (Role Switcher)」**。
可即時切換身分（Admin、Staff、悅眾、義工），系統會依據身分動態隱藏左側導覽列的選項（見 `components/layout/Sidebar.tsx` 與 `contexts/MockAuthContext.tsx`），幫助展示時的權限說明。

## 貳、暫停期間需要確定的事項（等待使用者回饋）

在預計長達一個月的 UAT 期間，需要向使用者確認以下重點，這些確認將會影響未來後端的實作細節：
1. **流程是否順暢**：表單中的「活動排程（四種模式）」操作是否符合實際派工的日常習慣？
2. **名冊處理流程**：Excel 匯入時，如果發現名字一樣但四眾編號不同的例外處理機制是什麼？
3. **身分權限覆蓋範圍**：「悅眾」在系統中是否只能看到自己被指派的特定活動？（目前的 Mock 設計是如此）。
4. **手機端閱讀**：請義工實際用手機開啟 RSVP 回覆頁，確認字體與按鈕大小是否足夠舒適。

## 參、未來開發計畫 (Phase 2 & Phase 3)

待使用者完成確認並重啟專案時，接下來的工程任務與實作藍圖如下：

### 階段二：資料庫建置與 API 串接 (Database & APIs)
1.  **資料庫連線**：使用 `Turso` (LibSQL) 取代目前的 Mock 資料。實作本地的 SQLite 方案加速開發。
2.  **Prisma 模型映射**：依據 `types/index.ts` 中定義的 `Profile`、`Activity` 等型別，正式編寫 `schema.prisma`。為避免衝突，所有的實體表名稱加上 `ch_` 前綴（如 `ch_profile`）。
3.  **取代 Mock 資料**：逐頁將各個 `page.tsx` 中引用的 `mockActivities` 或 `mockProfiles` 替換為 Next.js App Router 的 Server Actions 或 API Routes 呼叫。

### 階段三：核心功能打通 (Logic Implementation)
1.  **驗證機制 (Auth.js)**：實作真實的 Google OAuth，並在登入後自動連線資料庫驗證使用者的 `fourAsmId`。
2.  **Excel 真實解析**：導入 `SheetJS` (`xlsx` 套件)，撰寫前端上傳後解析成 JSON 的邏輯，並儲存進資料庫。
3.  **Brevo 信件派送**：串接 Brevo API，撰寫 `sendInvitationEmail` 函數，將 RSVP Token 轉換成信件點擊連結發出。
4.  **Audit Log 中介層**：建立統一的日誌紀錄服務，確保留下任何活動異動與人員狀態改變的足跡。
