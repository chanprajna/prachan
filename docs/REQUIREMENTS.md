# 法鼓山傳燈院活動管理網站 - 需求說明書 (v1.4)

> **版本歷程**: v1.3 → v1.4（2026-04-04）：補充 UI 先行確認流程、待確認事項、UI 驗收標準。

---

## 1. 專案目標與願景

建立一個模組化的線上平台，將法鼓山傳燈院的活動規劃、義工邀約及回覆作業數位化。首要目標是取代現有的手動文件處理，提升活動執行的效率與準確性，並建立可追蹤、具延續性的義工資料庫。

設計上須導入「現代禪風 (Modern Zen)」的 UI/UX，並提供淺色與深色模式 (Dark Mode)，讓使用者可以自行切換與啟動，保持介面的柔和與閱讀舒適度。
此外，須遵循**「以菩薩為中心」**的設計理念：考量使用者多為 40-70 歲的義工，UI 必須「大字、大按鈕、步驟清楚」，並且每一個操作都必須附帶清楚的中文確認提示。

| 角色層級 | 認證方式 | 權限範圍 |
| :--- | :--- | :--- |

## 3. 核心功能模組

### 3.1 系統管理與人員維護 (Profile Management)

*   **Google OAuth 連結**：首次登入時，若 Email 不匹配，需輸入四眾編號與手機驗證以完成連結。
*   **人員管理**：
    *   管理者可「手動新增」單筆人員資訊（含四眾編號、姓名、性別、Email、手機）。
    *   系統內四大角色（管理者、專職、悅眾、義工）在本質上皆為「人員資訊」，均可個別進行查找、新增或修改資料。
    *   指定人員之系統權限（Admin, Staff, Yue-Zhong）。

**UI 驗收重點**：
- 人員列表需有搜尋（姓名/四眾編號）與篩選（角色）功能。
- 新增/編輯人員使用彈窗（Modal）或側拉面板（Drawer）？ ← **待確認偏好**

### 3.2 活動與組別管理

*   **活動與預期排程 (Scheduling Engine)**：
    *   **排程時間設定**：所有活動皆需設定每日的「開始時間」與「結束時間」（如 09:00 到 17:00）。若為過夜活動，則視為整天。
    *   **類型一：單日活動**（不需過夜）。
    *   **類型二：兩天活動（不過夜）**：連續兩天往返。
    *   **類型三：兩天活動（過夜）**：包含第一晚住宿點名。
    *   **類型四：規律性週課**：自定義堂數（例如連續 8 週），指定每週固定星期與時段（例如週三 19:00 - 21:00）。
    *   **智慧順延功能**：提供功能選項，當規律週課遇國定假日（如連假）時，系統應能自動順延一週不排課。

*   **組別配置與維護**：
    *   預設提供「內護、外護、學長、文宣」等組別。
    *   **彈性調整**：專職可在活動進行期間「新增」自定義組別、「異動」名稱或名額、以及「停用」不再需要的組別（若已有邀約紀錄則採標記停用，不直接刪除資料）。

*   **群組通訊**：針對全活動或特定組別發送 Email 通告。

**待確認**：
- [ ] 活動建立後，是否允許修改活動類型（例如從單日改為兩天）？
- [ ] 規律性週課的各堂次是否需要個別管理（個別組別、個別邀約），或整批管理？
- [ ] 組別的「預設名額」是多少？是否可為 0（無上限）？

**UI 驗收重點**：
- 活動建立表單需清楚呈現四種排程類型的切換。
- 組別管理介面需顯示目前名額使用率（已確認/總名額）。

### 3.3 義工邀約與審核流程

1.  **Excel 上傳**：悅眾按組別上傳名冊。
2.  **資料 Upsert**：以四眾編號為準，異動時自動更新並紀錄 Log。
3.  **自動邀約**：發送含專屬連結的 Email。
4.  **RSVP 回覆**：義工線上點選「可護持/不克參與」，並可填寫意見。
5.  **悅眾審核**：
    *   **衝突提醒**：標註義工是否已在其他組別報名。
    *   **審核操作**：確認護持或拒絕（需填寫原因），系統顯示名額剩餘狀況。

**待確認**：
- [ ] 義工的 RSVP 回覆是否可以「多次修改」（在截止日前）？
- [ ] 邀約是否有截止日期設定？截止後是否自動關閉 RSVP 連結？
- [ ] 若義工沒有 Email，是否有備用的通知方式（如手機簡訊）？
- [ ] 「衝突提醒」是否需要跨活動（跨不同活動的組別衝突），或僅限同一活動內？

**UI 驗收重點**：
- RSVP 頁面須為手機優先設計，操作步驟不超過 2 步。
- 審核儀表板需用顏色或 Badge 清楚區分：待審核、已確認、已拒絕、衝突警示。

### 3.4 義工資料庫建置與維護 (核心邏輯)

*   **多元化建檔**：支援「後台手動新增」及「Excel 批次匯入」兩種方式。
*   **資料同步機制**：
    1.  透過 Excel 或手動輸入獲取「四眾編號」。
    2.  若編號不存在：自動在資料庫建立新的義工 Profile。
    3.  若編號已存在：比對內容，若關鍵聯絡資訊有異動，則自動更新資料並於 Audit Log 紀錄異動細節。
*   **長期累積**：隨著不同活動的舉辦與資料異動，系統將自動匯集成一份完整且具備歷史軌跡的傳燈院義工資料庫。

**待確認**：
- [ ] Excel 匯入時若欄位有缺漏（如缺少 Email），是否仍允許匯入，還是整列跳過並顯示警告？
- [ ] 匯入錯誤處理：哪些欄位是「必填」（阻擋匯入），哪些是「選填」（警告但仍匯入）？

---

### 3.5 信件版樣管理與測試 (Email Templates)

*   **信件版型設計**：後台提供 UI (例如簡易文字與變數插入編輯器)，讓專職與管理者可以自訂發信的內文版樣。
*   **動態變數支援**：信件內容可插入如 `{{活動名稱}}`、`{{義工姓名}}`、`{{RSVP連結}}` 等變數。
*   **發送測試功能**：在正式發送前，提供「發送測試信」按鈕，讓管理者可以收到實際信件，確認版型排版與變數替換是否正確。

## 4. 全域紀錄與安全性

*   **異動操作日誌 (Audit Log)**：所有「寫入動作」（建立、更新、審核、發信）皆須紀錄操作者、時間、舊值與新值。
*   **義工資料保護**：個資異動需完整保留變更紀錄 (Log Table)。

**待確認**：
- [ ] Audit Log 查詢功能的權限範圍：是否僅限 Admin 可查，還是 Staff / 悅眾也可查（限自己操作的紀錄）？
- [ ] 個資保護合規：是否需要符合台灣《個人資料保護法》的特定要求（例如資料保留年限、義工可申請刪除個資）？

## 5. UI 畫面確認流程（使用者驗收）

> **原則**：所有畫面以靜態 Mock 資料完成後，安排使用者逐功能確認，確認完畢才進入後端資料庫開發。

### 5.1 確認流程

1.  開發者完成靜態畫面 → 部署至 **UAT Preview 環境**。
2.  安排與使用者（專職 / 悅眾代表）進行 Demo。
3.  使用者填寫「畫面確認表」（可使用 Google 表單）記錄意見。
4.  開發者依回饋修改畫面。
5.  使用者確認無誤 → 簽核進入後端開發階段。
